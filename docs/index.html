Turn raw API failures into safe, useful engineering escalations.

Support Trace Analyzer is a local command-line tool that validates incident evidence, removes common secrets and personal data, assigns an explainable failure category, and creates a consistent Markdown or JSON report.

What it does

Support cases often begin with a screenshot, a copied response, or a message saying an API is “down.” Those reports are hard to investigate, and copied payloads can contain credentials that should never reach a ticket or chat channel.

Support Trace Analyzer provides a repeatable intake step before escalation:

  • Validate evidence. Reject impossible status codes, negative latency, malformed headers, and invalid fields.
  • Redact sensitive values. Remove secret-shaped keys, Bearer tokens, API keys, passwords, sk-… values, and email addresses recursively.
  • Classify the failure family. Route authentication, rate-limit, upstream, latency, request-contract, and unknown failures using readable rules.
  • Create the handoff. Include safe evidence, observations, next actions, reproduction steps, and escalation criteria.
  • Group repeated failures. Use a safe fingerprint that ignores volatile request IDs and timestamps.
Local by design: the tool makes no network requests. It does not upload evidence or call an AI model.

Who it is for and when to use it

It is intended for product support engineers, developer support teams, solutions engineers, API onboarding teams, and engineers who review customer escalations.

How it works

  1. 1

    Load and validate

    Accept one JSON object, an array, or JSONL, then check the evidence contract.

  2. 2

    Redact before output exists

    Nested dictionaries, arrays, headers, and bodies pass through the redaction boundary. Renderers only receive sanitized evidence.

  3. 3

    Apply inspectable triage rules

    Status codes and bounded evidence determine classification, severity, confidence, observations, and next actions.

  4. 4

    Fingerprint safe evidence

    A short SHA-256-derived fingerprint excludes request_id and occurred_at so repeated instances can group together.

  5. 5

    Write a report for review

    Receive Markdown for a human handoff or JSON for local automation. Every report asks for review.

Complete case story: from report to result

The problem

At 09:17, support receives “the production API is down” with a copied response. Forwarding it would leak a credential. Treating it as downtime would also misroute the case: the evidence is a fast 429 with a two-second retry instruction.

The investigation

Support previews a safe version with redact, checks the intake with validate, then uses analyze to create a rate-limit bundle containing the request ID, sanitized body, next actions, and reproduction.

The recurrence check

Three morning reports are passed to cluster. Because request IDs and timestamps do not affect the fingerprint, they group under 7b4755b5ccd192b9. This is evidence of a similar shape, not proof of one cause.

The result

Engineering receives one reviewed escalation instead of three screenshots. Support first checks Retry-After handling, bounded retries, and concurrency. If the issue persists, the request ID and reproduction are ready for deeper investigation.

What improved: no credential in the handoff, correct initial routing, fewer duplicate reports, and a clear escalation threshold.

Quick start

$ git clone https://github.com/Emmanuelasika/support-trace-analyzer.git
$ cd support-trace-analyzer
$ python -m venv .venv
$ source .venv/bin/activate
$ pip install -e .
$ tracekit analyze fixtures/rate-limit.json --output incident.md

Windows PowerShell activation: .venv\Scripts\Activate.ps1.

  • tracekit redact <input> — preview sanitized evidence.
  • tracekit validate <input> — validate JSON or JSONL.
  • tracekit analyze <input> --output <file> — create a report.
  • tracekit cluster <input> — count recurring fingerprints.

The core analysis module performs validation, redaction, classification, fingerprinting, and rendering without network or filesystem access. The CLI owns input and output. This keeps the sensitive boundary small and directly testable.

Limitations and tradeoffs

  • Redaction is pattern-based. Unusual secrets can evade it and innocent matches can be removed. Review the output.
  • It is not comprehensive DLP. Names, phone numbers, and arbitrary customer data are not detected.
  • Classification is a routing heuristic. It cannot inspect live health, SDK versions, account limits, logs, traces, or provider telemetry.
  • Fingerprints are clues, not incident IDs. Similar evidence can have different causes.
  • A human owns the handoff. There is no automatic ticket submission.
